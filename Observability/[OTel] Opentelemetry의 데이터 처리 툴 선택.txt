# Opentelemetry의 데이터 처리 툴 선택

# 목적
	- 오픈텔레메트리 콜렉터에서 보내는 로그를 EndPoint로 보낼 때 데이터를 가공해서 보내야함
		오픈텔레메트리 콜렉터 -> 데이터가공 -> 카프카 -> 아파치 스톰
	- 특정 필드의 데이터만 필요함


# 선결론
	- dataprepper 사용 -> 불가능
		- kafka 토픽 동적 처리 불가능
		- 카프카 토픽 수량만큼 필요하며, 이럴경우 콜렉터에서 분기처리를 해야함
		- 콜렉터에서의 분기처리의 경우 변경될 경우 매번 재기동이 필요함

	- fluent-bit 사용 -> 가능
		- kafka 토픽 동적 처리 가능
		- 로그만 전송하므로 경량화
		- 오픈텔레메트리 콜렉터에서 log안에 데이터를 전처리 하면 추가 필드 사용 가능

# 오픈텔레메트리 로그 규격 및 필요 필드
	- 필요한 데이터는 logRecords 배열에 들어있는 로그 데이터
	- 로그데이터 중에서도 body의 stringValue 와 traceId , spanId
	=====================================================================
	{
	  "resourceLogs": [
		{
		  "resource": {...},
		  "scopeLogs": [
			{
			  "scope": {...},
			  "logRecords": [
				{ 	
					"body": {
						"stringValue": "### LampController start"
						} 
					"traceId" : "ac21153b7a5579fd1a63ef7e0659379b",
					"spanId" : "ac21153b7a5579fd1a63ef7e0659379b"
					},
				{ /* log 2 */ },
				{ /* log 3 */ }
			  ]
			}
		  ]
		}
	  ]
	}
	=====================================================================

# fluent-bit

	- 플루언트 비트의 철학
		=====================================================================
		"로그 파이프라인은 가볍게,트레이스 상관관계는 OpenTelemetry Collector나 Backend에서"
		=====================================================================
		그래서 로그레코드 안의 바디 데이터(로그원문) 만 파싱해서 보내도록 설계 되어있음
	- 로그 데이터만 수집함
	- attribute 데이터 수집 불가
	- traceId , spanId 데이터 수집 불가
		-> 해당작업은 오픈텔레메트리 콜렉터에서 하면 로그내에서 확인 가능
	- 경량화
	- 처리 속도 빠름
	- 로그 데이터만 활용한다면 간단하게 사용가능
	- lua 기반
	- 수집된 데이터는 아래와 같이 저장됨
	=====================================================================
	v1_logs: [1769275011.1090294645, {"log":"### LampController start"}]
	v1_logs: [1769275011.1095956545, {"timestamp":"2026-01-25 02:16:51.232","service":"OG077201"}
	=====================================================================

# 기존 아키텍처
	애플리케이션 -> 파일비트 -> 카프카 -> 아파치스톰 -> ES

	1. 애플리케이션에서 "수집 규격"에 맞는 로그 파일 생성
	2. 파일비트가 해당 파일을 읽어 카프카로 보냄
		- 파일비트에는 어디로 보낼지 토픽이 설정되어 있음
		- 카프카에서 확인한 로그
		=====================================================================
		{
		  "@timestamp": "2026-01-23T02:56:21.897Z",
		  "@metadata": {
			"beat": "filebeat",
			"type": "doc",
			"version": "6.2.4",
			"topic": "TOPIC_LAMP"
		  },
		  "source": "/var/log/LAMP/ag/apigw_cus-tb-apigw-0_transaction.log",
		  "offset": 58191964,
		  "message": "{\"timestamp\":\"2026-01-23 11:56:14.944\",\"service\"...중략...}",
		  "beat": {
			"name": "filebeat-859pc",
			"hostname": "filebeat-859pc",
			"version": "6.2.4"
		  }
		}
		=====================================================================

	3. 아파치 스톰 클러스터 1~5번에서는 각각 토픽 1~5에 접근하여 데이터 처리
	4. 처리된 데이터는 ES에 저장


# 오텔 아키텍처

# 오텔 아키텍처 변경 점
	- 스톰 처리단계 수정 사항 최소화
	- 기존 파일비트 사용 서비스 + 오픈텔레메트리 사용서비스 동시 수용 가능
		message 필드로 로그 데이터를 한번 더 감싸서 기존 파일비트 수집서비스 + 신규 오픈텔레메트리 사용서비스를 둘다 수용 가능
	- 오픈텔레메트리 에이전트 활용으로 인하여 기존 LAMP로그 규격만이 아닌 OTLP 규격의 로그,트레이스,메트릭을 수집함
	- 로그규격내에 trace id 를 추가해서 추후 트레이스와 메트릭을 활용한 기능 개발 가능
